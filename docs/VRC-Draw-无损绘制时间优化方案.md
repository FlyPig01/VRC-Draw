# VRC-Draw 无损绘制时间优化方案

方案日期：2026-07-26
状态：核心方案已执行并通过全量离线零差异验证

本文中的12张样本数字是2026-07-26执行无损优化时的固定历史结果，不应替换为当前样本数。截至2026-07-27，仓库的 `sample` 目录已有14张图片；最新路径质量、耗时和内存结果见[线稿与真实绘制路径质量改进方案](VRC-Draw-真实绘制路径矢量拟合方案.md)。

## 1. 目标与不可妥协条件

下一阶段的目标是减少VRChat中的实际绘制时间，优先减少鼠标左键按下次数和抬笔移动时间。

本方案中的“无损”不是“肉眼看起来差不多”，而是要求：

1. 不修改当前已经确认的高分辨率线稿。
2. 不删除任何有效轮廓、内部结构或短线。
3. 不增加路径简化误差。
4. 不通过降低处理分辨率换取速度。
5. 不添加原路径中不存在的连接线。
6. 每一条原始路径边仍然完整绘制，允许反向绘制，但默认不允许重复绘制。
7. 优化前后的离线最终绘制覆盖必须完全一致；只要存在一个差异像素，就自动放弃优化结果并回退到原路径。
8. 继续保持相邻左键按下至少间隔600 ms，不能重新引入双击召唤橡皮的问题。
9. 默认不改变落笔状态下的最大单步、移动等待和按钮时序。

因此，本阶段首先优化“怎样把完全相同的路径一次连续画完”，而不是优化“少画一些内容”。

## 2. 当前耗时来源

当前流程把路径图中的大部分图边分别输出为独立 `Stroke`。每条笔画都会生成：

```text
抬笔移动到起点
→ 落笔前等待16 ms
→ 左键按下
→ 落笔后等待16 ms
→ 按路径移动，每次移动后等待16 ms
→ 左键抬起
→ 抬笔后等待32 ms
→ 下一次左键按下前保证至少间隔600 ms
```

当前12张质量样本合计：

| 指标 | 当前结果 |
|---|---:|
| 笔画数 | 10,762 |
| 矢量路径点 | 112,627 |
| 相邻落笔间隔数量 | 10,761 |
| 仅按600 ms计算的落笔时间跨度下限 | 6,456.6秒，即107.61分钟 |
| 每笔固定16+16+32 ms的累计量 | 688.77秒，即11.48分钟 |

这里的107.61分钟不是完整绘画时间预测，而是从第一次落笔到最后一次落笔，仅由防双击规则形成的理论下限。实际路径移动如果已经消耗了部分或全部600 ms，就不会重复补满同一段时间。

当前耗时可以分为四类：

| 耗时类别 | 是否影响画面 | 本阶段处理方式 |
|---|---|---|
| 落笔路径移动 | 直接影响 | 默认完全不改变 |
| 左键按下/抬起与600 ms保护 | 不改变路径几何，但次数过多 | 通过无损合并共享端点的路径减少次数 |
| 抬笔移动 | 不产生线条 | 优化笔画顺序、方向和闭环起点 |
| 图片处理和路径生成 | 不计入VRChat实际绘制时间 | 只要求不能明显回退 |

因此，优先级应当是：

```text
减少左键次数
→ 减少抬笔距离
→ 再评估其他时序优化
```

## 3. 什么叫“压缩笔画但不压缩画面”

程序当前将交叉点的每条图边分别作为一笔。例如一个X形交叉通常是4条图边、4次落笔。但相对的两条边可以在同一个交点连续通过：

```text
当前：左上→中心，抬笔；中心→右下，抬笔
优化：左上→中心→右下，只落笔一次
```

两种情况经过的几何线段完全相同。优化没有删除线段，只是取消交点处多余的“抬起后在同一位置再次按下”。

这一问题可以建模为无向多重图：

- 节点：路径端点和交叉点。
- 边：已经通过质量验证的每一条实际路径。
- 一笔：不重复经过图边的一条连续迹。

对于一个连通分量，如果奇数度节点数量为 `O`，在每条边恰好绘制一次的条件下，理论最少笔画数为：

```text
O = 0 时：1笔
O > 0 时：O / 2笔
```

示例：

| 结构 | 当前按边输出 | 无重复边的理论最少笔画 |
|---|---:|---:|
| 单个闭环 | 1 | 1 |
| 被拆成多段的连续长线 | 多笔 | 1 |
| X形交叉 | 4 | 2 |
| T形交叉 | 3 | 2 |
| Y形交叉 | 3 | 2 |
| 多个互不连接的图形 | 不能跨图形合并 | 每个连通分量分别计算 |

这个方法不会像笔画上限那样牺牲细节，也不会用一条新直线连接两个相近但实际不相连的端点。

## 4. 总体架构

建议把当前流程调整为：

```text
高分辨率线稿
→ 质量优先的路径图提取
→ 保留节点、图边和原始边编号的 RouteGraph
→ 无损笔画优化器
   ├─ 严格可连接性判断
   ├─ 最少无重复边迹分解
   ├─ 闭环起点选择
   └─ 抬笔顺序与方向优化
→ 质量等价门禁
   ├─ 原始边完整性
   ├─ 逻辑路径覆盖一致
   └─ 实际鼠标执行覆盖一致
→ 生成 ExecutionPlan
→ 路径预览和实际执行
```

线稿提取和路径质量算法不参与此次压缩。优化器接收已经确认正确的路径，只改变边的组合、绘制方向和顺序。

## 5. 阶段一：保留路径图，不立即展平成独立笔画

### 5.1 当前问题

`TraceSkeleton` 内部已经拥有：

- `SkeletonNode`。
- `GraphEdge`。
- 图邻接关系。
- 拟合后的交叉点。
- 被清理的毛刺标记。

但函数末尾立即把每条 `GraphEdge` 转换成一个独立 `Stroke`，随后只进行最近端点排序。图的拓扑信息在这一步丢失，后面无法判断哪些笔画本来就连接在同一个节点。

### 5.2 建议数据结构

```cpp
using RouteNodeId = std::uint32_t;
using RouteEdgeId = std::uint32_t;

struct RouteEdge {
    RouteEdgeId id{};
    RouteNodeId left{};
    RouteNodeId right{};
    Stroke points;
    bool leftJoinable{};
    bool rightJoinable{};
};

struct RouteGraph {
    std::vector<PointF> nodes;
    std::vector<RouteEdge> edges;
    std::vector<Stroke> standaloneStrokes;
};

struct EdgeVisit {
    RouteEdgeId edge{};
    bool reversed{};
};

struct OptimizedTrail {
    std::vector<EdgeVisit> visits;
    Stroke points;
};
```

`standaloneStrokes` 用于闭环、极小组件以及无法安全挂接到图节点的路径。它们继续完整保留。

### 5.3 严格可连接条件

两条边只有同时满足以下条件才能取消中间的抬笔：

1. 在 `RouteGraph` 中属于同一个节点。
2. 拟合后的浮点端点严格相同，并且转换到最终鼠标执行坐标后仍是同一个整数坐标。
3. 合并时不需要插入任何新的移动线段。
4. 两条边都没有被质量清理阶段标记为删除。
5. 合并后的路径通过最终覆盖一致性验证。

如果交叉点拟合失败，两条图边保留的是不同的真实骨架入口，就不能因为它们“距离很近”或“取整后碰巧重合”而强制连接。这样可以避免重新产生跨越白色区域的线。

## 6. 阶段二：最少无重复边迹分解

### 6.1 核心算法

对每个可连接的图连通分量执行无重复边迹分解：

1. 统计每个节点的有效度数。
2. 找出所有奇数度节点。
3. 使用带虚拟边的Hierholzer算法生成欧拉路线。
4. 在虚拟边处切分，得到 `max(1, O/2)` 条实际路线。
5. 删除虚拟边，确认每一条真实边恰好出现一次。
6. 将每条路线中的图边按访问方向拼接成一个 `Stroke`。

虚拟边只用于算法切分，不会进入最终路径，也不会生成鼠标移动。

### 6.2 交叉点转向选择

满足最少笔画数可能存在多种走法。应在不改变笔画下限的前提下，优先选择切线最连续的组合：

- X形交叉优先让相对方向的边连续通过。
- T/Y形交叉优先连接夹角最接近直线的两条边。
- 避免在交点处进行没有必要的急转弯。
- 如果不同走法的笔画数和转向代价相同，再选择有利于下一笔抬笔距离的方案。

转向代价只决定“先画哪条边”，不能删除或修改图边。

### 6.3 禁止通过重复描线换取更少笔画

中国邮差算法可以通过重复某些边，把一个有很多奇数节点的图变成一条欧拉回路。但这会重复描线，可能造成VRChat画笔局部变粗，因此本阶段明确禁止。

规则是：

```text
每条原始图边访问次数必须严格等于1
```

宁可多保留几次安全落笔，也不能通过重复经过已有线条换取更低的笔画数。

## 7. 阶段三：无损减少抬笔移动

完成连续路线合并后，剩余路线之间仍需抬笔移动。此时可以进行以下不改变画面的优化。

### 7.1 路线方向选择

每条开放路线都允许正向或反向绘制。选择离上一笔终点更近的一端作为起点，不改变该路线覆盖的线段。

### 7.2 闭环起点旋转

闭环的任意点都可以作为起点。当前闭环起点由骨架遍历位置决定，可能离上一笔很远。优化时可以：

1. 在闭环已有路径点中选择距离当前鼠标最近的点。
2. 循环旋转点数组，使该点成为首尾点。
3. 比较顺时针和逆时针方向。

闭环几何和全部路径点保持不变。

### 7.3 全局路线排序

当前最近端点排序是逐步贪心，容易早期选择一个局部近邻，导致后续出现很长的空笔跳转。

建议使用：

```text
空间网格或轻量KD-tree建立近邻候选
→ 最近端点生成初始顺序
→ 仅在近邻候选中执行带方向的2-opt改进
→ 对闭环重新选择起点
```

优化目标不使用单纯欧氏距离，而使用 `InterpolateMouseLine` 在当前 `maximumPenUpStep` 下实际会生成的移动命令数。这样优化的是实际等待时间。

为保持轻量化，使用C++23和自实现空间索引，不引入第三方图优化库。

### 7.4 不改变空笔输入参数

虽然增大空笔单步或缩短空笔等待看起来不会直接画线，但Windows相对鼠标加速度和VRChat输入采样可能使最终起点发生变化。为满足“绝对不能降低质量”，本阶段保持：

- `maximumPenUpStep=6`。
- `penUpMoveInterval=16 ms`。

只减少空笔总距离，不改变每个空笔事件的输入特征。

## 8. 阶段四：执行计划中的无损规范化

优化路径转换到实际鼠标坐标后，再执行一次只针对完全等价命令的规范化：

1. 删除连续目标坐标完全相同且不会触发按钮行为的空移动。
2. 合并相邻的等待命令，但不减少等待总时长。
3. 检查每条合并路线只包含原始边，不含新连接段。
4. 重新计算左键次数、各类等待和预计总时长。

默认不执行以下操作：

- 删除转换后长度很小的笔画，因为一次原地落笔可能仍会留下点。
- 合并“距离小于某个阈值”的端点。
- 增大落笔最大单步。
- 缩短落笔移动的16 ms等待。
- 缩短600 ms防双击间隔。

## 9. 质量等价门禁

优化结果不能直接交给执行器。必须先通过四层门禁；任何一层失败，都自动使用优化前路径。

### 9.1 图边完整性

为每条原始图边分配稳定ID，验证：

```text
优化前有效边ID集合 == 优化后边ID集合
并且每个边ID在优化后出现且只出现1次
```

边可以反向访问，但点序列只能是原序列或原序列的完全反转。

### 9.2 逻辑路径覆盖一致

用相同画布、相同线宽和相同栅格化规则分别渲染优化前后路径，逐字节比较二值覆盖图：

```text
新增像素数 = 0
缺失像素数 = 0
异或差异像素数 = 0
```

不采用SSIM、PSNR或“差异低于1%”之类的近似阈值。

### 9.3 鼠标执行覆盖一致

分别生成优化前后的 `ExecutionPlan`，模拟全部鼠标命令：

1. 还原每一个落笔状态下的整数鼠标位置。
2. 使用与路径预览相同的线段栅格化规则生成执行覆盖图。
3. 比较两张执行覆盖图，要求差异像素为0。
4. 验证最终鼠标坐标相符。
5. 验证所有原始落笔线段仍然存在。

允许变化的只有：

- `LeftDown`/`LeftUp` 数量减少。
- 笔画顺序和方向变化。
- 抬笔移动路线缩短。
- 因落笔次数减少而消失的等待。

### 9.4 安全时序不变量

自动化测试继续验证：

- 任意两次实际 `LeftDown` 至少间隔600 ms。
- 每次暂停、恢复或重新开始都不能绕过该间隔。
- 落笔移动最大单步仍为2～6。
- 落笔移动后仍等待16 ms。
- 落笔前后和抬笔后的等待规则不变。

## 10. 进度与剩余时间

笔画合并后，一条路线可能比当前单笔长很多。如果进度仍只在 `LeftUp` 时增加，悬浮窗会长时间不变化。

建议把内部进度改为基于执行计划累计权重：

```text
绘制进度 = 已完成计划权重 / 总计划权重
预计剩余 = 未执行命令的累计预计时间
```

权重可以由落笔移动长度和计划等待时间组成，并在每个移动命令完成后更新。普通用户仍只看到：

- 绘制进度百分比。
- 预计剩余时间。

不向用户显示图边数、鼠标命令数、奇数节点数或优化算法参数，也不增加新的普通用户设置。

暂停时不计入剩余绘制时间；恢复后根据剩余命令重新计算。长路线中途暂停时，执行器仍会立即抬起鼠标，恢复时遵守600 ms保护后从当前位置继续。

## 11. 性能统计

在 `ExecutionPlan` 内部增加仅供开发验证的分类统计：

```cpp
struct ExecutionPlanMetrics {
    std::size_t sourceEdges{};
    std::size_t strokesBefore{};
    std::size_t strokesAfter{};
    std::size_t leftDownCount{};
    std::size_t penDownMoves{};
    std::size_t penUpMoves{};
    std::chrono::milliseconds penDownMoveTime{};
    std::chrono::milliseconds penUpMoveTime{};
    std::chrono::milliseconds buttonGuardWait{};
    std::chrono::milliseconds fixedButtonWait{};
    std::chrono::milliseconds totalTime{};
};
```

不能只报告“笔画减少百分比”。最终报告至少需要逐图列出：

- 优化前后笔画数。
- 优化前后左键按下次数。
- 优化前后抬笔移动次数和距离。
- 600 ms保护实际补充了多少等待。
- 落笔移动时间是否完全不变。
- 预计总时长和节省比例。
- 三层覆盖一致性检查结果。

每删除一笔最多可以消除：

- 一次左键按下和抬起。
- 64 ms固定按钮等待。
- 最多600 ms的落笔间隔约束。
- 一段抬笔移动。

这些时间存在重叠，不能直接相加；最终节省时间必须由优化前后完整 `ExecutionPlan` 重新计算。

以下仅说明笔画数量对600 ms理论下限的影响，不是预计优化结果：

| 笔画数 | 相邻落笔时间跨度下限 |
|---:|---:|
| 10,762 | 107.61分钟 |
| 5,000 | 49.99分钟 |
| 3,000 | 29.99分钟 |
| 1,000 | 9.99分钟 |

实际能降到多少必须由真实路径图的奇数度节点数量决定，方案阶段不预设虚假目标。

## 12. 测试方案

### 12.1 图算法单元测试

增加以下合成图：

- 单线和被拆段的长线。
- 开放折线。
- 闭环。
- X、T、Y、V交叉。
- 多个相连闭环。
- 含多个奇数度节点的复杂图。
- 多个互不连接的组件。
- 端点很近但不相连的两条线。
- 拟合失败、节点入口不同的交叉区域。

每个测试同时验证理论最少笔画数、每条边访问一次以及覆盖图零差异。

### 12.2 执行计划测试

- 优化前后落笔覆盖逐像素相同。
- 优化后 `LeftDown` 数量等于优化后笔画数。
- 600 ms防双击约束继续成立。
- 暂停发生在长路线中间时能够安全抬笔和恢复。
- 剩余时间随每个命令推进，不因长笔画停止更新。
- 路径预览继续只来自最终执行命令。

### 12.4 VRChat实机A/B

离线零差异只能证明软件发送的最终绘制几何等价，不能替代VRChat对连续输入的实际采样验证。正式启用前仍需在相同世界、画笔、视角和图片下进行：

1. 使用未优化路径绘制一次。
2. 使用优化路径绘制一次。
3. 人工检查交叉点、闭环接缝、细小眼睛和长曲线。
4. 重点检查连续穿过交叉点是否出现局部变粗、断点或转向抖动。
5. 只要发现任一退化，保留运行时回退并不启用该类连接。

测试过程不读取VRChat内存、不注入游戏、不自动分析游戏状态，继续只使用普通鼠标输入，符合现有安全边界。

## 13. 明确不采用的“提速”方式

以下方式可能明显提速，但与“绝对不能降低质量”冲突，本方案不采用：

- 提高笔画简化误差。
- 删除短笔画或小组件。
- 设置笔画上限。
- 降低1536线稿处理分辨率。
- 按距离阈值连接原本分离的端点。
- 在墨迹内部增加捷径。
- 重复描线以换取单笔欧拉回路。
- 增大落笔最大单步。
- 缩短落笔移动等待。
- 缩短600 ms防双击间隔。
- 为减少时长而跳过颜色较浅或“看起来不重要”的线。
- 使用AI重新生成更简单的线稿。

如果以后要研究时序加速，应建立单独的实验分支和VRChat实机基准；在没有证明质量等价前不能进入默认版本。

## 14. 资源、依赖与存储

### 运行内存

路线图只是在现有图边基础上增加节点ID、边ID和访问方向。以当前112,627个路径点计算，主要点数据仍约为1 MB量级。验证阶段同时保留基准路径和优化路径，预计额外占用数MB，远小于高分辨率图像处理约78 MB的峰值工作集。

通过质量门禁后即可释放临时基准覆盖图和优化图，避免在绘制期间长期占用内存。

### 发布体积

- 继续使用C++23。
- 不引入Qt、OpenCV、Boost Graph、AI模型或其他大型依赖。
- 图遍历、空间网格和有限候选2-opt使用标准库实现。
- 发布包体积预计无明显变化。

### 文件存储

- 正式版本的优化结果只保存在内存中。
- 开发验证图写入软件目录下的 `build/draw-time-validation`。
- 如以后保存诊断报告，也必须位于软件目录内。
- 不写入注册表、用户文档、AppData或其他系统位置。
- 删除整个软件目录仍可完全清除全部数据。

## 15. 推荐实施顺序

### 第一步：只增加耗时分类统计

不改变任何路径和执行行为，先得到12张样本逐图的真实时间组成，确认600 ms保护、落笔移动和抬笔移动各自占比。

### 第二步：保留 `RouteGraph` 和稳定边ID

重构 `TraceSkeleton` 的输出边界，但暂时仍按一边一笔生成路径。要求重构前后的路径与执行覆盖完全一致。

### 第三步：实现严格端点连接和无重复边迹分解

只合并不需要新移动线段的图边；加入边ID唯一访问检查和自动回退。

### 第四步：优化闭环起点、路线方向和抬笔顺序

保持所有落笔参数不变，仅减少空笔移动命令。

### 第五步：改造进度和剩余时间

改为按执行计划累计权重持续更新，避免长笔画期间进度停滞。

### 第六步：全量离线零差异验证

生成12张样本的基准/优化路径图、执行图和指标报告。任何样本不满足零差异时，定位并禁用对应优化，不降低验收条件。

### 第七步：VRChat实机验证

实测连续交叉、闭环和长线。实机确认前，不研究落笔采样间隔或最大单步提速。

## 16. 最终建议

第一版只实施以下三项：

1. 共享端点图边的无重复边迹合并。
2. 闭环起点、笔画方向和抬笔顺序优化。
3. 优化前后逻辑路径与鼠标执行覆盖的零差异门禁。

这是当前唯一能够在不删除内容、不降低分辨率、不增加简化误差、也不修改落笔时序的情况下，显著减少左键次数和绘制时间的方向。

在第一版得到真实数据前，不承诺固定的压缩比例。最终是否接受优化结果只由“质量零差异”和“预计时间确实下降”共同决定；任一条件不满足，就继续使用当前路径。

## 17. 正式实施结果

实施日期：2026-07-26

### 17.1 已实现内容

本方案的第一版已经完成：

1. 新增独立的 `PathOptimizer` 模块。
2. 将质量阶段输出的每条笔画视为带稳定索引的无向图边。
3. 只把浮点端点严格相同的图边归入同一个节点。
4. 使用虚拟边和Hierholzer算法，将每个连通分量分解为最少的无重复边迹。
5. 虚拟边只参与算法切分，不会产生鼠标移动。
6. 每条原始边保留结束索引，合并后仍按原边边界计算曲率采样。
7. 闭环只允许在原始图边边界上改变起点，不从边的中间切开。
8. 开放路线允许反向，整数插值改为方向对称，反向路线严格使用同一批采样点的逆序。
9. 最近端点初始排序后，使用48路线窗口、最多两轮的方向感知2-opt降低空笔移动。
10. 增加逻辑线段和最终落笔鼠标线段的双重精确门禁。
11. 增加预计时间门禁；优化后没有变快时自动保留原路径。
12. 绘制进度改为按已完成的计划毫秒数更新，高精度等待每16 ms累计一次。
13. 转换到实际鼠标坐标后没有移动的点状笔画保持独立落笔，避免丢失可能由单次按下产生的点。

内部的 `ImageProcessingOptions::optimizeDrawingTime` 仅用于开发A/B验证，默认启用，没有加入普通用户界面。

### 17.2 自动回退条件

优化结果必须同时满足：

```text
优化前后逻辑线段多重集完全相同
且每一条线段的出现次数完全相同
且优化前后落笔鼠标移动线段多重集完全相同
且落笔移动命令数量完全相同
且优化后笔画数不增加
且优化后预计时间不增加
```

任意条件失败，`OptimizeDrawingPathLossless` 会直接返回优化前路径。质量门禁在正式运行路径中执行，不只存在于测试代码。

### 17.3 方向对称采样

全量验证初期发现，同一线段正向和反向执行时，浮点比例取整顺序可能产生不同的中间整数点。正式实现改为：

1. 按端点字典序确定规范方向。
2. 只在规范方向生成一次整数采样点。
3. 反向绘制时严格反转该点序列。
4. 每条线段的单步取两端曲率要求中更保守的值。

最大单步仍为2～6，每个移动事件后仍等待16 ms。该修改不会让采样变稀，并保证路径方向优化不改变最终鼠标移动覆盖。

路径渲染器也按相同方式规范线段方向，消除浮点运算顺序造成的最低位抗锯齿差异。

### 17.6 尚需实机确认的边界

离线验证已经证明程序生成的落笔几何、整数鼠标移动线段和预览覆盖没有变化；按钮次数、空笔路线和线段执行方向发生了变化。VRChat对连续穿过交叉点时的具体笔刷采样仍属于外部行为，无法只依靠离线算法证明。

因此，正式发布前仍建议使用当前样本重点实测：

- X/T/Y交叉点连续通过。
- 闭环接缝。
- 细小眼睛和睫毛。
- 长曲线反向绘制。
- 暂停后恢复长笔画。

实测不需要也不允许读取VRChat内存或注入游戏。若某类连续连接在实机中出现退化，可以在不影响其他图边的情况下把该节点标记为不可连续，并继续保留其余无损优化。
